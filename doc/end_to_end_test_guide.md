## エンドツーエンドテストシナリオ

### シナリオ1: 申請作成から実行まで

#### ステップ1: 申請作成
1. 管理者でログイン
2. ユーザー一覧から対象ユーザーを選択
3. ユーザー編集画面に移動
4. レベル変更申請セクションで新しいレベルを選択
5. 管理者パスワードと変更理由を入力
6. 申請を作成

**期待結果:**
- 申請が正常に作成される
- 「申請が作成されました。変更は○年○月○日に実行されます」のメッセージが表示
- データベースにpending状態の申請が保存される

#### ステップ2: 申請確認
1. 申請管理画面にアクセス
2. 作成した申請が一覧に表示されることを確認
3. 申請詳細画面で内容を確認

**期待結果:**
- 申請一覧に新しい申請が表示される
- 申請詳細で正しい情報が表示される
- ステータスが「申請中」になっている

#### ステップ3: ユーザー詳細での申請表示確認
1. 対象ユーザーの詳細画面にアクセス
2. 申請中の情報が表示されることを確認

**期待結果:**
- 基本情報に「申請中」の項目が表示される
- 変更内容と実行予定日が正しく表示される

#### ステップ4: バッチジョブの手動実行
```bash
# Rakeタスクで手動実行
bundle exec rake level_change:execute
```

**期待結果:**
- ジョブが正常に実行される
- ユーザーのレベルが変更される
- 申請ステータスがcompletedに更新される
- user_level_historiesに履歴が作成される

#### ステップ5: 実行結果の確認
1. ユーザー詳細画面でレベルが変更されていることを確認
2. 申請管理画面で申請ステータスが「完了」になっていることを確認
3. レベル履歴に新しい履歴が追加されていることを確認

### シナリオ2: 申請キャンセル

#### ステップ1: 申請作成
- シナリオ1のステップ1と同様

#### ステップ2: 申請キャンセル
1. 申請管理画面にアクセス
2. 対象申請の「キャンセル」ボタンをクリック
3. 確認ダイアログで「OK」をクリック

**期待結果:**
- 申請がキャンセルされる
- ステータスが「キャンセル」に更新される
- ユーザーのレベルは変更されない

### シナリオ3: エラーハンドリング

#### ステップ1: 重複申請の防止
1. 既に申請があるユーザーに対して再度申請を作成
2. エラーメッセージが表示されることを確認

#### ステップ2: バリデーションエラー
1. 管理者パスワードを空にして申請
2. 変更理由を空にして申請
3. 適切なエラーメッセージが表示されることを確認

### シナリオ4: インセンティブ計算の確認

#### ステップ1: レベル変更前の購入
1. 対象ユーザーの子孫ユーザーで購入を実行
2. インセンティブが変更前のレベルで計算されることを確認

#### ステップ2: レベル変更実行
- バッチジョブでレベル変更を実行

#### ステップ3: レベル変更後の購入
1. 同じ子孫ユーザーで購入を実行
2. インセンティブが変更後のレベルで計算されることを確認

## パフォーマンステスト

### 大量データでのテスト

#### データ準備
```ruby
# 100件の申請を作成
100.times do |i|
  user = User.create!(
    name: "テストユーザー#{i}",
    email: "user#{i}@test.com",
    password: "password123",
    level: Level.find_by(name: "代理店")
  )
  
  LevelChangeApplication.create!(
    user: user,
    current_level: user.level,
    target_level: Level.find_by(name: "総代理店"),
    applicant: admin,
    reason: "テスト用申請#{i}",
    scheduled_date: Date.current
  )
end
```

#### パフォーマンス測定
```bash
# 実行時間を測定
time bundle exec rake level_change:execute
```

**期待結果:**
- 100件の申請が5分以内に処理される
- メモリ使用量が適切な範囲内
- エラーが発生しない

### 問題が発生した場合の対処

1. **ログを確認**
   - `log/development.log`でエラー内容を確認
   - スタックトレースを分析

2. **データベースの状態を確認**
   ```ruby
   # 申請データの確認
   LevelChangeApplication.all
   
   # レベル履歴の確認
   UserLevelHistory.recent.limit(10)
   ```

3. **ロールバック手順**
   - 必要に応じてマイグレーションをロールバック
   - テストデータを削除
   - 元の状態に復元
